# RFC 0001：意图驱动的实时媒体运行时

- 状态：Accepted
- 日期：2026-08-04
- 影响版本：v0.2+

## 决策

`aimedia` 从“双机位 AI 导播产品”调整为面向开发者和集成商的实时媒体运行时：

> 用户声明输入、目标输出、质量、延迟和故障策略；图编译器生成可解释的执行计划，
> 运行时负责有界执行、监控和恢复。

自动导播继续保留，但属于可选策略和官方示例，不再决定核心类型、配置和路线图。

项目不会重写所有 codec，也不追求 FFmpeg 的全格式覆盖。差异化集中在长期媒体作业的
编译、资源规划、故障隔离、可观测性和 AI 扩展边界。

## 为什么不是重新建仓库

现有 MPEG-TS、SRT、AAC、NVIDIA 边界、独立节目时钟和有界调度都属于新运行时的
数据面基础。需要改变的是上层产品模型，而不是推翻底层代码。重开仓库会丢失历史和
兼容证据，并让个人项目同时维护两个不完整实现。

因此采用渐进接管：新图编译器先描述现有单路链路，随后运行时改为执行编译后的计划；
旧的导播专用类型最后再迁移。

## 三个平面

### 控制平面

接收媒体作业配置或 API 请求，完成校验、能力探测、资源准入、启动、更新和停止。
控制平面不搬运视频帧。

### 实时数据平面

执行 transport、demux、decode、timeline、process、encode、mux 和 output 节点。每条边
都有固定容量和明确的满载策略，任何节点不得创建无界媒体队列。

### 智能与事件平面

通过非阻塞 `AnalyzerTap` 接收抽样帧、PCM 和运行指标，输出带时间和置信度的事件。
AI 失败不能阻塞实时数据平面。自动导播、字幕、审核和精彩片段识别都构建在这一层。

## 图编译契约

配置描述目标，`aimedia-graph` 生成 `ExecutionPlan`。每个节点记录：

- 节点职责和是否属于关键链路；
- 运行数据位于主机内存还是 NVIDIA 显存；
- 当前实现状态，避免把接口骨架误报为可用后端。

每条连接记录：

- 媒体类型，例如 MPEG-TS、H.264 access unit、NV12 frame 或 f32 PCM；
- 时钟域：输入源时钟、独立节目时钟或控制事件时钟；
- 内存域；
- 队列容量；
- 队列满时等待、丢旧数据、只保留最新数据或终止作业。

`aimedia explain` 必须只输出编译器生成的计划，不能维护另一套手写拓扑。

## 目录和包命名

仓库路径位于 `crates/` 下时已经具有上下文，因此目录使用短名称：

```text
crates/
  aac/
  cli/
  core/
  graph/
  mpegts/
  nvidia/
  runtime/
  srt/
```

Cargo 包名继续使用 `aimedia-*`，因为包名会出现在 workspace 外部和 crates.io 全局
命名空间中。也就是说：目录避免重复，公开包保留品牌和防冲突前缀。

## 配置迁移

v0.1 的 `DirectorPipeline` 配置暂时继续解析，作为图编译器的输入适配层。下一版配置
将采用 `MediaJob`，把字段整理为 `inputs`、`processing`、`outputs`、`taps` 和
`failurePolicy`。在新执行器接管真实单路链路前，不同时维护两套运行时。

## 分阶段迁移

1. 建立 `aimedia-graph` 和可解释的类型化执行计划。
2. 让现有单路 SRT 调度器使用图中的队列容量和资源约束。
3. 完成原生单路数据面，把图节点状态升级为真实支持。
4. 引入 `MediaJob` 配置，并为 v0.1 配置提供一次显式转换工具。
5. 将导播、VLM 和双机位策略移入可选扩展层。
6. 增加多输出、AI Tap 和服务化作业生命周期。

## 非目标

- 用 Rust 重写全部 H.264、AAC、AV1 等 codec；
- 复制 FFmpeg CLI 的全部参数；
- 成为任意节点均可连接的 GStreamer 克隆；
- 建设观众侧 CDN、播放器或桌面直播工作室；
- 为尚未验证的协议和平台声明生产支持。

## 代价

- 一段时间内会同时存在通用媒体作业术语和旧导播配置字段；
- 图编译器需要与实际执行器持续做差分验证，防止“计划能生成、运行却不一致”；
- 显式资源、时间和故障契约增加了前期类型设计工作；
- 支持矩阵会比 FFmpeg 窄，但每个支持组合必须更可预测、更容易运维。
