# 用户故事

本文把“第二阶段完成”翻译成用户可以观察和验收的行为。尚未实现的自动 AI 能力不混入本阶段故事。

## 第一次接触直播开发的小白

**前提**：用户有 Linux x86_64、Docker、NVIDIA GPU 和两路符合支持矩阵的测试流。

**操作**：按照快速入门复制示例配置，运行环境检查和 `aimedia explain`，再启动节目。

**期望结果**：

- 工具用中文指出 Docker、GPU、驱动、SDK或配置是否满足要求。
- 用户能看到“两路输入、一个节目输出、当前镜头”的简单状态。
- 专有名词都能从术语表跳转到解释，不要求先理解媒体协议。

**异常情况**：缺少 NVIDIA runtime、端口占用或密钥引用不存在时，启动在打开直播前失败，并给出可执行的修复提示。

## 直播平台开发者

**前提**：两路 SRT/MPEG-TS 输入都是 H.264 1080p30、AAC-LC 48kHz 双声道。

**操作**：启动 `aimedia run`，通过 `aimedia control take` 切换机位，再恢复 `auto`。

**期望结果**：

- 两路持续解码，切镜不等待输入关键帧。
- 输出连接和节目时钟连续，播放器不需要重新连接。
- 健康机位的 Take 在 100ms 内生效，切换同时触发输出 IDR。
- 音频跟随目标机位，80ms 淡化期间没有明显爆音或静音洞。

**异常情况**：目标机位断流、冻结或偏差超过 80ms 时，Take 被拒绝并返回稳定错误码，不先切入坏画面。

## 直播运维人员

**前提**：节目以 Docker 容器部署，SRT 网络存在抖动和临时断线。

**操作**：查询 `aimedia control state --json`，观察日志和队列水位，并模拟一路输入断开。

**期望结果**：

- 状态包含 RTT、丢包、重传、重连次数、时间偏差和队列水位。
- 当前机位断开时自动切到健康备用机位；备用机位断开不打断当前节目。
- 每个队列都有固定上限，断网时内存不会持续增长。
- 日志不显示 passphrase、token 或敏感 Stream ID。

**异常情况**：两路都不可用时保持最后一帧并输出静音；GPU OOM 或编码器不可恢复错误导致管线明确失败，而不是假装继续运行。

## 控制台集成开发者

**前提**：控制台与 aimedia 进程运行在同一 Linux 主机或共享 Unix Socket。

**操作**：发送带 `requestId` 的 `take`、`auto` 和 `state` JSON 消息。

**期望结果**：

- 每个请求只产生一个带相同 `requestId` 的响应。
- 响应包含 `accepted`、稳定错误码和命令执行后的状态。
- `holdMs: 0` 一直保持人工模式，直到显式调用 `auto`。
- socket 默认权限为 `0660`，没有默认开放网络端口。

**异常情况**：非法 JSON、未知命令、重复请求或越界保持时间不会导致控制服务或媒体任务退出。

## 开源贡献者

**前提**：贡献者没有 NVIDIA GPU 或未安装闭源 SDK。

**操作**：运行默认 Cargo 检查、CPU 测试、回放和 fuzz smoke。

**期望结果**：

- 核心、MPEG-TS、控制协议和 mock runtime 可以在纯 CPU CI 编译测试。
- NVIDIA、libsrt 和 libxaac 均位于特性开关后的独立边界。
- 不需要 FFmpeg 才能编译产品；FFmpeg 只允许出现在互操作测试容器中。

**异常情况**：启用原生特性但缺少 SDK 时，构建脚本明确报告缺少的库、版本和准备步骤。
